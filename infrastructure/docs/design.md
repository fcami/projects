# Single Repository for Multiple Open-Source Projects — Design Document

## Original Prompt

> As a GitHub user, I want a single repo to host all my opensource projects so that I can keep track of them easily. This git repo has to be CI-friendly whether CI be Azure CI or GitHub actions or something else, language agnostic (subprojects could be C/C++/Python/Rust/etc) and robust (triggers on repo commit/merge/push). Each subproject should follow similar rules derived from Booch/Gamma/Lakos/Beck/Fowler teachings. Explain how you would do it, do not do it. The first goal is to document the how. Also tell me if there is an author I should add to the mix.

Generated by Claude Opus 4.6 (1M context) via Claude Code on 2026-04-17. The following authors were added to the mix beyond those in the original prompt: Robert C. Martin (Clean Architecture, SOLID, component cohesion/coupling principles), Jez Humble and Dave Farley (Continuous Delivery, deployment pipelines), and Titus Winters, Tom Manshreck, and Hyrum Wright (Software Engineering at Google, monorepo practices at scale).

**Standing instruction for any future change or review of this document:** always ask "Should I include other principles from other authors? If yes, list the authors and why."

## Claude Code Consumption Note

This document describes how to structure a single Git repository (monorepo) hosting multiple independent open-source subprojects. When the user asks to implement this design, follow these steps in order:

1. **Create the directory skeleton**: `projects/`, `infrastructure/ci/`, `infrastructure/templates/new-project/`, `.github/workflows/`, `.azure-pipelines/`.
2. **Write `infrastructure/ci/detect-changes.sh`**: a portable shell script that compares the current changeset against `projects/*/` and outputs a JSON array of affected subproject names. Use `git diff --name-only` against the merge base.
3. **Write `infrastructure/ci/setup-toolchain.sh`**: reads each subproject's `ci.yaml` (which declares `language`, `version`, and any extra dependencies) and installs the appropriate toolchain.
4. **Write `infrastructure/ci/run-project-ci.sh`**: a thin dispatcher that runs `make -C projects/$PROJECT lint build test` and collects exit codes.
5. **Write `.github/workflows/ci.yaml`**: the GitHub Actions entry point using the detect/fan-out pattern described below. Keep logic in `infrastructure/ci/` scripts, not in YAML.
6. **Write `.azure-pipelines/pipeline.yaml`**: same pattern, different YAML surface, same `infrastructure/ci/` scripts.
7. **Write `infrastructure/templates/new-project/`**: scaffold containing a `Makefile` (with all contract targets stubbed), a `ci.yaml` template, a `README.md` template, and a `CHANGELOG.md` template.
8. **Write the top-level `README.md`**: list all subprojects, link to each, explain the contract, explain how to add a new subproject.
9. **Migrate existing subprojects**: for each project to import, copy its source into `projects/<name>/`, write a `Makefile` implementing the contract by delegating to the project's native build system, write a `ci.yaml` declaring its toolchain, and verify `make lint build test` passes locally.

Each subproject's `Makefile` is an adapter: it translates the uniform contract targets into language-specific commands. The contract is the stable interface; the implementation behind each `Makefile` varies by language and toolchain.

Do not introduce a monorepo build system (Bazel, Nx, Turborepo) unless the user explicitly requests one or cross-project dependencies become complex. The `make` + shell approach is simpler, fully language-agnostic, and transparent.

## Core Insight

The key tension is: **one repo** but **independent subprojects**. The solution is a uniform contract at the build boundary — every subproject, regardless of language, presents the same interface to CI and to humans.

This is what Humble and Farley call the **deployment pipeline as architecture**: the pipeline is not an afterthought bolted onto the code — it is a first-class architectural element that shapes how components are organized, built, and validated. The uniform contract is the seam between "how the code is structured" and "how the pipeline validates it."

## The Uniform Contract (Beck + Gamma + Martin)

Every subproject, regardless of language, must expose these targets via a top-level `Makefile` (or a thin wrapper that calls `cargo`, `pytest`, `cmake`, etc.):

| Target | Purpose |
|---|---|
| `make build` | Compile / prepare |
| `make test` | Run all tests |
| `make lint` | Static analysis, linting |
| `make fmt-check` | Verify formatting (no mutation) |
| `make fmt` | Apply formatting |
| `make clean` | Remove build artifacts |
| `make release` | Produce release artifact (optional) |

This is the **Interface Segregation Principle** (Gamma/Martin) applied to build systems: CI programs to the contract, not to the implementation. A Rust project's `make build` calls `cargo build`; a C project's calls `cmake --build`. CI doesn't care.

Martin's **Dependency Inversion Principle** is also at work here: the CI pipeline (a high-level policy module) does not depend on Cargo, CMake, or pytest (low-level details). Both depend on the `Makefile` contract (an abstraction). This is what makes the system language-agnostic — adding a Go subproject requires zero CI changes, only a `Makefile` that implements the contract.

Each subproject also has:
```
projects/foo/
├── Makefile              # Implements the contract
├── README.md             # What, why, how to use
├── CHANGELOG.md          # User-facing changes
├── ci.yaml               # Toolchain declaration (language, version)
├── src/                  # Source (language-specific layout beneath)
└── tests/                # Tests co-located or adjacent
```

### Martin's Component Cohesion: What Belongs in a Subproject

Robert C. Martin's three component cohesion principles govern what belongs together:

- **REP (Reuse-Release Equivalence Principle)**: the unit of reuse is the unit of release. Each subproject must be independently releasable and independently useful. If something can't be released on its own, it shouldn't be a separate subproject — merge it into its consumer.
- **CCP (Common Closure Principle)**: gather into a subproject those things that change for the same reasons and at the same times. If a bug fix or feature always touches both module A and module B, they belong in the same subproject.
- **CRP (Common Reuse Principle)**: don't force users to depend on things they don't use. If a subproject contains utilities that only one consumer needs, move them into that consumer rather than making everyone depend on the utility subproject.

These three principles are in tension — REP and CCP push toward larger subprojects (more cohesive, fewer releases), while CRP pushes toward smaller ones (less unnecessary coupling). The balance shifts over time as the codebase evolves.

## Change Detection and Fan-Out (Lakos + Humble/Farley)

This is where **Lakos's physical design** thinking meets **Humble and Farley's deployment pipeline** thinking. The CI pipeline has two stages:

**Stage 1 — Detect.** Compare the changeset against `projects/*/`. Produce a list of affected subprojects. If `infrastructure/ci/` or root config changed, mark all subprojects affected.

**Stage 1b — Infrastructure.** When the infrastructure itself changed, it runs its own contract (`infrastructure/Makefile`: shellcheck and flake8 for `lint`, a bash test suite for `test`) before any subproject, and the fan-out is skipped if it fails. The tooling every subproject depends on is held to the same contract as the subprojects. It stays in `infrastructure/`, not `projects/`: it is not an independent subproject, and its changes must keep triggering every subproject. The CI scripts accept the reserved name `infrastructure` for it, and `new-project.py` refuses that name.

**Stage 2 — Fan-out.** For each affected subproject, run the contract targets in a parallel job/matrix entry. Each subproject builds and tests in isolation.

```
on push/PR:
  detect-changes → [project-a, project-c]
  ┌─────────────────┐   ┌─────────────────┐
  │ project-a        │   │ project-c        │
  │  make lint       │   │  make lint       │
  │  make build      │   │  make build      │
  │  make test       │   │  make test       │
  └─────────────────┘   └─────────────────┘
```

This is CI-system-agnostic by design. `detect-changes.sh` is a portable shell script that outputs a JSON list. GitHub Actions consumes it as a matrix; Azure Pipelines consumes it as a variable; any other CI reads it as a list. The CI-specific config is a thin adapter.

Humble and Farley emphasize that **the pipeline must give fast feedback**. The fan-out pattern achieves this: changing one subproject does not rebuild the entire monorepo. Only the affected subproject (and its dependents, if any) are validated.

They also stress that **every stage of the pipeline must be automated and repeatable**. No manual steps, no "run this script on your laptop first." The `infrastructure/ci/` scripts must work identically in CI and locally — a developer should be able to run `infrastructure/ci/detect-changes.sh` and `make -C projects/foo test` on their own machine to reproduce exactly what CI does.

## Dependency Management Between Subprojects (Lakos + Martin)

Lakos's **levelization** principle: if subproject B depends on subproject A, then A is at a lower "level" and must build first. Circular dependencies between subprojects are forbidden.

Martin formalizes this as the **Acyclic Dependencies Principle (ADP)**: the dependency graph of components must be a directed acyclic graph (DAG). If a cycle appears, break it by extracting the shared dependency into a lower-level subproject or by inverting the dependency using an interface/trait.

Martin adds two more coupling principles:

- **SDP (Stable Dependencies Principle)**: depend in the direction of stability. A subproject that many others depend on should be hard to change (stable). A subproject that nothing depends on is free to change (unstable). Don't make an unstable subproject depend on another unstable subproject — that creates fragility chains.
- **SAP (Stable Abstractions Principle)**: stable packages should be abstract. If a shared library is depended on by many subprojects and is therefore stable, it should expose abstract interfaces rather than concrete implementations, so that stability doesn't prevent extension.

In practice, for a personal portfolio of independent projects, there are usually **no cross-project dependencies** — each subproject is level-0. If shared code emerges, extract it to `projects/shared-lib/` and treat it as a lower-level component. CI builds it first, then fans out to its dependents.

Maintain a simple dependency declaration (even if it's just a comment or a YAML file) so CI can topologically sort the build order when needed.

## Per-Subproject Design Principles

These are the rules each subproject follows internally, synthesized from the authors.

### From Lakos (Large-Scale Software Design)
- **Physical and logical design align.** Directory structure mirrors module/component structure. No "utils" junk drawers.
- **Acyclic dependencies.** Between internal modules, between subprojects — no cycles, ever.
- **Components testable in isolation.** Each module can be built and tested without the full project.
- **Minimize transitive dependencies.** A component should depend on what it directly uses, nothing more.

### From Beck (XP / TDD / Simple Design)
- **Four rules of simple design**, in priority order: (1) passes all tests, (2) reveals intention, (3) no duplication, (4) fewest elements.
- **Tests are first-class artifacts.** They live next to source, they run fast, they're part of the contract.
- **YAGNI.** Don't build abstractions for hypothetical future needs. Three concrete cases before you generalize.
- **Small, frequent commits.** Each commit leaves the project in a working state.

### From Gamma (Design Patterns / GoF)
- **Program to interfaces, not implementations.** At module boundaries, define clear contracts.
- **Favor composition over inheritance.** Especially relevant for C++/Rust/Python.
- **Open/Closed Principle.** Modules should be open for extension, closed for modification — at the boundary, not everywhere.

### From Booch (OO Analysis and Design)
- **Encapsulation.** Hide internal details. Expose only the necessary interface.
- **Clear component boundaries.** Each subproject has a defined public API or user-facing surface.
- **Separation of concerns.** Distinct responsibilities in distinct modules.

### From Fowler (Refactoring / CI)
- **Continuous integration.** Every push to the trunk triggers validation. Broken builds are fixed immediately.
- **Refactoring discipline.** Improve internal structure without changing external behavior. Separate "behavior change" commits from "structure change" commits.
- **Short-lived branches.** Merge frequently. Don't let branches diverge far from trunk.

### From Martin (Clean Architecture / SOLID / Component Principles)
- **Single Responsibility Principle.** Each module has one reason to change. Each subproject serves one coherent purpose.
- **Open/Closed Principle.** Structure modules so new behavior can be added without modifying existing code — via traits, interfaces, or extension points.
- **Liskov Substitution Principle.** When a module promises an interface, any implementation must honor the full contract. This applies to the `Makefile` contract too: if `make test` is defined, it must actually run tests.
- **Interface Segregation Principle.** Don't force consumers to depend on interfaces they don't use. Keep public APIs narrow.
- **Dependency Inversion Principle.** High-level policy should not depend on low-level details. Both should depend on abstractions. In the monorepo context: CI depends on the `Makefile` contract, not on `cargo` or `pytest` directly.
- **The Dependency Rule (Clean Architecture).** Dependencies point inward — from volatile, concrete outer layers toward stable, abstract inner layers. Within a subproject, I/O and framework code depend on domain logic, never the reverse.

### From Humble and Farley (Continuous Delivery)
- **Everything in version control.** Source, tests, CI configuration, infrastructure scripts, documentation — all in the repo. No tribal knowledge, no "run this on the build box."
- **Automate everything.** If a human has to remember a step, it will eventually be forgotten. The pipeline is the single source of truth for "how to build and validate this."
- **Build binaries once.** Don't rebuild for different environments. Build once in CI, promote the same artifact through stages.
- **Fast feedback.** The pipeline should tell you within minutes whether your change is broken. Parallelize aggressively. If a stage is slow, make it faster or move it later in the pipeline (but never skip it).
- **Deployment pipeline as the backbone.** The pipeline is not a nice-to-have — it is the architectural spine that keeps the monorepo honest. If a subproject can't go through the pipeline, it doesn't belong in the repo yet.

### From Winters, Manshreck, and Wright (Software Engineering at Google)
- **Hyrum's Law**: with a sufficient number of users of an API, all observable behaviors of your system will be depended on by somebody. This means: be deliberate about what you expose. Internal implementation details that leak become de facto API. In a monorepo, even internal subprojects can develop implicit consumers.
- **Code review as a quality gate.** Every change goes through review. In a single-person monorepo, this means: don't merge your own PRs without at least running the full pipeline. Self-review with a time gap substitutes for a second pair of eyes.
- **Large-scale changes.** When a cross-cutting change is needed (updating a shared dependency, changing the contract), make it atomically across all affected subprojects in a single commit or PR. Don't leave the repo in a half-migrated state.
- **Dependency management at scale.** Prefer vendoring or lockfiles over floating version ranges. Reproducible builds require pinned dependencies. Each subproject owns its dependency pins.
- **One version rule.** If two subprojects depend on the same external library, they should agree on the version. In a monorepo, version skew between subprojects creates subtle bugs. (This is less critical when subprojects have no cross-dependencies, but matters if shared libraries emerge.)

## CI Configuration Strategy

The CI entry point is CI-system-specific but minimal. The logic lives in `infrastructure/ci/` as portable shell scripts.

**GitHub Actions** (`.github/workflows/ci.yaml`):
```yaml
on:
  push:
    branches: [main]
  pull_request:

jobs:
  detect:
    runs-on: ubuntu-latest
    outputs:
      matrix: ${{ steps.detect.outputs.matrix }}
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - id: detect
        run: echo "matrix=$(infrastructure/ci/detect-changes.sh)" >> "$GITHUB_OUTPUT"

  build:
    needs: detect
    if: needs.detect.outputs.matrix != '[]'
    strategy:
      matrix:
        project: ${{ fromJson(needs.detect.outputs.matrix) }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: infrastructure/ci/setup-toolchain.sh ${{ matrix.project }}
      - run: make -C projects/${{ matrix.project }} lint
      - run: make -C projects/${{ matrix.project }} build
      - run: make -C projects/${{ matrix.project }} test
```

**Azure Pipelines** follows the same pattern with a different YAML surface. The `detect-changes.sh` and `setup-toolchain.sh` scripts are shared.

`setup-toolchain.sh` reads a `ci.yaml` in each subproject to know what to install (Rust toolchain, Python version, C compiler, etc.).

## Triggers

- **Push to `main`**: run affected subprojects' full CI.
- **Pull request**: run affected subprojects' full CI. Report per-subproject status checks.
- **Tag `projects/foo/v*`**: run `make release` for that subproject. Optionally publish artifacts.
- **Scheduled (weekly)**: run all subprojects regardless of changes — catches dependency rot, upstream breakage.

Humble and Farley would add: the **commit stage** (lint, build, test) should complete in under 10 minutes. If it doesn't, split slow tests into a second pipeline stage that runs after the commit stage passes. Fast feedback on the common case; thorough validation before merge.

## Licensing

Each subproject can define its own license independently. A Git repository is a distribution mechanism, not a legal unit. What determines license interactions is the **dependency graph**, not the directory tree. Co-habitation in a single repo does not cause licenses to "infect" each other.

### Rules

1. **Each subproject gets its own `LICENSE` file.** Place it at `projects/foo/LICENSE`. GPL, LGPL, MIT, BSD, Apache — whatever fits that subproject's goals.
2. **The root `LICENSE` covers infrastructure only, not subprojects.** This repo uses the [REUSE specification](https://reuse.software/) to make license scoping machine-verifiable. Every infrastructure file has an `SPDX-FileCopyrightText` and `SPDX-License-Identifier` header; files that can't carry headers are covered by `REUSE.toml`. The `LICENSES/` directory contains the canonical license texts. Run `reuse lint` to verify compliance. Without per-file license metadata, license scanners interpret a root LICENSE as applying to the entire repository — a root MIT would allow anyone to ignore a subproject's GPL/LGPL copyleft by choosing the MIT terms instead.
3. **Independent subprojects have no license interaction.** If subproject A is GPL and subproject B is MIT, and neither depends on the other, both licenses govern only their own code. There is no conflict.
4. **Cross-project dependencies create license obligations.** If subproject B (MIT) incorporates or links against subproject A (GPL), then B's distribution must comply with the GPL. This is a dependency-graph question, not a repo-layout question. The monorepo design in this document defaults to independent subprojects (all level-0, no cross-dependencies), so this is unlikely to arise.
5. **Shared libraries must use a compatible license.** If `projects/shared-lib/` emerges and is consumed by subprojects under different licenses, it must use a license compatible with all consumers. In practice, this means the most permissive option (MIT, BSD, or Apache 2.0) for shared code.

### LGPL for Libraries

The LGPL was designed to allow libraries to be open-source while permitting any code — open or proprietary — to use them. This is its primary purpose, and it achieves it well. glibc, GTK, Qt (historically), and many FFmpeg components are LGPL, and they are used by proprietary software at massive scale without issue.

The LGPL requirements are straightforward:

1. **Usage is unrestricted.** Any code may link against an LGPL library and remain under any license, including proprietary. This is the normal case.
2. **Modifications to the LGPL library itself must be released under LGPL.** If you fix a bug or add a feature in the library, that change is LGPL. Your consuming code is unaffected.
3. **The user must be able to swap in a modified version of the LGPL library.** This is the one operational requirement. With dynamic linking (`.so`, `.dll`) — the default on every major desktop and server platform — this is satisfied automatically. The user replaces the shared library file and the consuming application picks it up.
4. **Static linking requires providing re-linkable object files.** If you statically link an LGPL library into a binary, you must provide the object files (`.o`) or source necessary for the user to re-link against a modified version of the library. This is a narrower requirement that matters mainly in embedded/firmware contexts or language toolchains that default to static linking (some Rust/Go configurations). On desktop/server platforms with standard dynamic linking, this clause rarely comes into play.

For this monorepo: if a shared library under `projects/shared-lib/` is LGPL, consumers within or outside the repo simply link against it dynamically — which is the default behavior — and no further obligations arise beyond keeping the library's own modifications LGPL.

### Copyright Ownership and Relicensing

A license is a grant of rights FROM the copyright holder TO third parties. It does not constrain the copyright holder. The copyright holder can always:

- Use their own work under any license, regardless of what license they granted to others.
- Copy their own MIT-licensed code into a GPL subproject without any MIT obligation.
- Relicense their own work at any time, under any terms.

This is fundamental copyright law. The license governs what *others* may do with the work. The author is never bound by their own license grant.

**Implications for this monorepo:**

1. **The infrastructure templates** (`infrastructure/templates/`) are MIT-licensed. The copyright holder can copy them into any subproject under any license — GPL, LGPL, proprietary, anything — with no MIT obligation on the copies. No provenance concern, no dual-licensing risk.
2. **Third-party forks** are different. If someone else forks this repo and uses the MIT templates in their own GPL subproject, MIT permits this — MIT explicitly allows unrestricted use, modification, and relicensing. The copies become part of the GPL project. This is by design: MIT was chosen for the infrastructure precisely because it is compatible with every license.
3. **Rule of thumb:** MIT code can flow into any license. GPL/LGPL code cannot flow into MIT. Choose the infrastructure license (MIT) to be the most permissive, so it never blocks a subproject's license choice.

### Monorepo Infrastructure License

The root `LICENSE` is standard MIT. The [REUSE specification](https://reuse.software/) provides the scoping: every infrastructure file carries SPDX copyright and license headers. Files that can't carry headers (templates, `.gitkeep`) are covered by `REUSE.toml`. The `LICENSES/MIT.txt` file contains the canonical license text. `reuse lint` verifies that every file in the repository has explicit license metadata.

The infrastructure is MIT-licensed because:
- MIT is compatible with every open-source license (GPL, LGPL, BSD, Apache, etc.).
- The copyright holder can use MIT-licensed infrastructure in subprojects under any license without restriction.
- Third parties who fork the repo can also use the infrastructure under any license — MIT permits this unconditionally.
- Per-file SPDX metadata prevents the MIT from being interpreted as applying to subprojects, protecting copyleft (GPL/LGPL) subprojects from dual-licensing. This scoping is machine-verifiable via `reuse lint`.

## What NOT To Do

- **Don't use a monorepo build system** (Bazel, Nx, Turborepo) unless you have 20+ subprojects with heavy cross-dependencies. For a personal portfolio of independent projects, `make` + shell scripts is simpler, more transparent, and language-agnostic by nature. Winters et al. describe Google's monorepo tooling, but Google has 2+ billion lines of code. Adopt their principles, not their infrastructure.
- **Don't share CI caches across unrelated subprojects.** Each subproject caches its own build artifacts keyed by its own lockfile/dependency hash.
- **Don't enforce a single language's conventions on all subprojects.** The uniform contract is at the `Makefile` level, not at the source level. Rust projects use `src/lib.rs`; Python projects use `src/foo/__init__.py`; C projects use `src/*.c`. That's fine.
- **Don't half-migrate.** If you change the contract (add a new target, rename an existing one), update all subprojects atomically. A half-migrated repo violates the contract's value as a stable interface.
- **Don't skip the pipeline.** Even for "trivial" changes. Humble and Farley: "the pipeline is the only authority on whether a change is safe." If the pipeline is too slow for trivial changes, make the pipeline faster — don't bypass it.

## Recommended Reading

These are the works this design draws from, in suggested reading order:

1. **Robert C. Martin** — *Agile Software Development: Principles, Patterns, and Practices* (2002) and *Clean Architecture* (2017). The component cohesion and coupling principles (REP, CCP, CRP, ADP, SDP, SAP) are the most directly applicable to monorepo subproject design. SOLID principles govern internal module design.

2. **John Lakos** — *Large-Scale C++ Software Design* (1996). Despite the C++ focus, the physical design and levelization concepts are language-agnostic and essential for dependency management in any multi-component system.

3. **Kent Beck** — *Extreme Programming Explained* (2nd ed., 2004) and *Test-Driven Development: By Example* (2002). The four rules of simple design and YAGNI keep each subproject lean.

4. **Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides** — *Design Patterns* (1994). "Program to interfaces" and "favor composition" are foundational. The uniform `Makefile` contract is a Strategy pattern applied at the build system level.

5. **Grady Booch** — *Object-Oriented Analysis and Design with Applications* (3rd ed., 2007). Component boundaries, encapsulation, separation of concerns.

6. **Martin Fowler** — *Refactoring* (2nd ed., 2018) and various articles on CI/CD. The refactoring discipline (separate structural changes from behavioral ones) and CI principles.

7. **Jez Humble and Dave Farley** — *Continuous Delivery* (2010). The deployment pipeline as an architectural element. Fast feedback, automation, repeatable builds. This is the definitive reference for the CI/CD strategy described here.

8. **Titus Winters, Tom Manshreck, Hyrum Wright** — *Software Engineering at Google* (2020). Monorepo practices at scale, Hyrum's Law, large-scale changes, dependency management. Adopt the principles selectively — the infrastructure is Google-scale, but the thinking applies everywhere.
